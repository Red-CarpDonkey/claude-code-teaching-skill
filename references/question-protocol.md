# 用户提问中断处理协议

当教学过程中用户临时提出疑问时，Skill 按以下流程处理。此协议确保提问被认真对待而不打断教学主线，同时防止提前泄露后续阶段的内容。

## 第一步：问题分类

收到提问后，先判断属于哪一类：

| 类型 | 判断标准 | 示例 |
|------|---------|------|
| **A. 不理解** | 对当前正在讲的概念表示困惑 | "没懂"、"什么意思"、"能不能换个说法" |
| **B. 前探** | 问了当前元阶段之后才展开的内容 | 动因确立阶段问底层实现原理 |
| **C. 偏离** | 问的是当前主题之外的内容 | 学C++时问Git用法 |
| **D. 痛点提前** | 工程师模式中，在第五步之前问"这解决什么问题" | 在看使用模板时就问"为什么不直接new delete" |

## 第二步：元阶段门控

每个元阶段对可回答的问题类型有硬性边界。门控规则源于元阶段的教学目标——该阶段只做一件事，回答不该回答的问题会破坏学习效果。

### 元阶段 I：动因确立

本阶段唯一目标是制造认知缺口。除了帮助用户理解当前困境本身的澄清性提问，其他一概暂缓。

- **A 类**：答。用更浅显的表达帮助用户理解当前困境（不是理解"答案"，是理解"问题本身"）。
- **B 类**：暂缓。"这个问题很重要，但它会在我们深入时自然浮现。现在先记住这个困惑。"
- **C 类**：暂缓。简短说明"这超出了当前范围"，记录后回到主线。
- **D 类**：暂缓。不适用（工程师模式阶段一通常不涉及具体概念）。

### 元阶段 II：本体解构

本阶段目标是将概念拆解清晰。可回答理解类问题，不可提前跳到因果推演。

- **A 类**：立即降层到更浅表达（概念引入方法第四步/五步模板暂不触发的新降层）。不可用另一个术语解释此术语。
- **B 类**：记录到延迟问题队列。"到推演的时候你会看到——这个问题会在你动手时自己浮出答案。"
- **C 类**：2-3句回答后明确回到主线。"这和当前主题的关系是[一句话]，但我们先聚焦在[当前概念]上。"
- **D 类**：暂缓。"你已经感觉到了关键。跑完代码你会看到答案。先试试？"

### 元阶段 III：因果建模

本阶段目标是让用户自己推导。用户的提问暴露的是真实思维路径，鼓励但只搭脚手架不直接给答案。

- **A 类**：用引导性反问帮助用户自己理清。"你卡在哪一步？上一步推导出了什么？"
- **B 类**：可以回答。此时用户已在深入，前探问题往往表明思维走到了前面，应鼓励。
- **C 类**：简短回答后回主线。
- **D 类**：暂缓。"代码跑完再看。你的疑问会在结果中自己解答。"

### 元阶段 IV：辩证审视

本阶段本身就是质疑和审视。所有问题都鼓励。

- **全部类型**：回答。

### 元阶段 V：范式融合

本阶段是连接和迁移。所有问题都鼓励，且应主动引导用户自己做跨领域连接。

- **全部类型**：回答。优先用反问引导用户自己建立连接。

### 门控速查表

| 元阶段 | A 不理解 | B 前探 | C 偏离 | D 痛点提前 |
|--------|---------|--------|--------|-----------|
| I 动因确立 | ✓ 答 | ✗ 暂缓 | ✗ 暂缓 | — |
| II 本体解构 | ✓ 答 | ✗ 记录延迟 | ~ 简短答 | ✗ 暂缓 |
| III 因果建模 | ✓ 引导不直接答 | ✓ 答 | ~ 简短答 | ✗ 暂缓 |
| IV 辩证审视 | ✓ 答 | ✓ 答 | ✓ 答 | ✓ 答 |
| V 范式融合 | ✓ 答 | ✓ 答 | ✓ 答 | ✓ 答 |

## 第三步：按类型回答

### A 类回答模板

遵循对应模式的概念引入方法：
- 工程师模式：五步实操模板的降层版（回到更浅的类比）
- 其他模式：通用三步的降层

**禁止行为：**
- 用另一个术语解释此术语
- 跳过"是什么"直接给公式/代码
- 说"这个很简单"、"你只需要记住..."

### B 类回答模板

**句式：** "这个问题很好——[肯定用户的前探直觉]。但它会在我们进入[目标阶段]时自然浮现。先记住这个困惑，它很重要。"

**动作：** 写入 `state.json` → `deferred_questions` 队列。

### C 类回答模板

**句式：** "[2-3句简短回答]。[一句话关联当前主题]。现在回到[当前阶段]——"

**约束：** 回答不超过3句话，不展开，不引入新术语链。

### D 类回答模板（仅工程师模式）

**句式：** "你已经感觉到了关键。跑完这段代码，你会看到答案。先试试？"

**约束：** 绝不提前描述痛点的具体内容。不暗示"这段代码展示了XXX原理"。

## 第四步：记录与回到主线

每次提问处理完成后执行：

1. **写入板书**：作为侧栏（用 `> 💬 提问：[问题]` 引用格式），插入在当前教学内容之前，不打断教学内容的流
2. **工程师模式**：生成 `[疑问]-[简短标题].md` 文件
3. **B类问题**：写入 `state.json` → `deferred_questions` 数组：
   ```json
   {
     "question": "用户原始问题",
     "deferred_from_meta_stage": "II",
     "target_meta_stage": "III",
     "timestamp": "2026-06-08T...",
     "status": "pending"
   }
   ```
4. **回主线声明**：CLI 中明确说"回到刚才的[阶段名/元阶段名]——"，拉回教学主线

## 第五步：延迟问题回访

当教学推进到延迟问题的目标阶段时，Skill 主动调出队列，融入当前教学内容：

> "还记得之前在[阶段]你问过'[问题]'吗？现在正是回答它的时候。"

回答后更新 `state.json` 中该问题的 `status` 为 `"answered"`。

教学全部完成后，检查 `deferred_questions` 是否全部回答。未回答的逐个处理，不留遗漏。

## 多问题连锁处理

用户一次提多个问题时：
1. 按类型优先级排序：A > D > B > C（先处理理解障碍，再处理痛点提前，再处理前探，最后处理偏离）
2. 同类型多个问题时，先回答与当前阶段最相关的
3. 一次只处理一个问题，处理完再处理下一个
4. 每个问题处理完毕后，回到主线一次
